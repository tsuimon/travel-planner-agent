# 复杂需求理解与验收

更新：2026-09-25。目标是让模型结合上下文选择下一步操作，再由程序执行和校验；模型理解得通，不等于路线、班次和预算已经核实。

## 模型主导的对话入口

配置LLM且 `CONVERSATION_AGENT=true` 时，自然语言请求首先进入 `ConversationAgent`。原有关键词路由不会先决定这是行程修改、问政策还是保存偏好。显式结构化API请求和未配置模型的演示流程仍走原有搜索入口。

模型读取最近会话、当前草稿与候选摘要，输出经过Pydantic校验的JSON动作：

- `probe`：只读查询指定日期的路线、上车站和方向的末班信息；可以继续选择另一个时间查询。
- `plan`：新行程、修改行程或假设试算。修改只合并明确字段；试算不覆盖当前草稿。
- `lookup`：受限的地点、天气、政策、网页线索工具。
- `remember`：用户明确要求的长期偏好。
- `reply`：回答或针对缺失信息追问。

查询结果返回给模型后继续决策，最多6步，共享30秒deadline和8000 Token预算。新规划在执行前再进行一次语义复核；显式活动起止时间由程序计算时长。长上下文先压缩旧对话文字、候选摘要，保留当前约束。Token预留在收到有效usage后按实际用量结算，失败或缺失usage仍保守保留预留量。

对于路线探查，最终的具体末班与接续事实由程序根据数据展示，而非直接采用模型自由生成的时刻建议。整条路线被淘汰时，仍保留已能核验的前半段接驳和线路运营时间；线路始发末班与上车站末班分开。赶上一条线不代表后续换乘成功。

模型失败或耗尽预算时返回已查询证据，保留当前行程，不再悄悄落回规则并声称“已收到行程修改”。API响应的 `metadata.conversation` 记录决策动作、是否试算和最后一次工具观察，便于排查；不记录模型内部推理。

- 新增 `test_conversation_agent.py`，验证只读追问、假设与修改分离、到达期限、无上下文澄清、非法动作修复、预算失败时上下文保留、活动时间计算和语义复核；这些是受控模型输出的执行契约测试，不代表任意语言理解准确率。

- 真实模型、隔离规划器的语义验收：多站例子保留9月26日15:00出发、19:30演唱会开始、22:00结束、150分钟活动、随后一小时用餐、最后广州；最终到达期限为空，交通预算500元。该条只验证语义，不证明完整路线已经可行。

模型仍可能误选动作或错误解释文字；语义复核不能保证消除所有错误。真实地图也可能匹配错场馆或校区，现有规划器的地点选择仍需继续改进。天气、机票库存、店铺排队等也不因引入对话决策而自动获得数据。

## 原有离线规则流程（保留兼容）

1. 读取当前会话的地点、活动、日期和约束。明确的新单程请求替换旧行程；后续修改基于当前行程。
2. 模型提取非固定句式，规则保留能确定的时间角色、数字和禁用条件。模型结果经 Schema 校验，失败会修复重试，再使用规则兜底；不能可靠处理的修改要求补充明确地点或时刻。
3. 区分出发窗口、最终到达期限、活动开场及活动时长。只有“4点到”且无上午/下午语境时先澄清，回复“下午”继续原请求。
4. 规划器传播活动结束后的可出发时间，累计计算费用、步行、骑行和换乘。违反硬限制的候选被淘汰，缺少价格的数据保留“预算未核实”标记。
5. 返回候选、淘汰原因、假设及数据缺口。完成部分行程时明确标注未完成部分。

|---|---|---|
| “下午四点到”“到达时间是下午4点”“最晚16:00” | 16:00为到达期限，重新查询倒推的出发时刻 | semantic_scenarios |
| “不是下午4点出发，是下午4点到” | 不把被否定的出发时刻用于规划 | semantic_scenarios |
| “明天出行”“次日01:00到” | 保留出发日期，明确跨日到达 | semantic_scenarios、parser_memory |
| “4点到”→“下午” | 保留原地点、预算和禁用方式后继续 | semantic_scenarios |
| 行程后说“不要打车”→“预算80元”→“可以打车” | 每轮重新规划；只修改对应条件；不把本次修改自动变成长久偏好 | semantic_scenarios |
| “目的地改成保定，出发推迟一小时” | 模型更新对应字段，规则不以旧地点覆盖；模型失败时请求明确新地点/时刻 | semantic_scenarios |
| “只能走五百米”“步行不超过1.5公里”“最多换一次” | 转为累计距离、换乘硬上限；模型失败时这些明确数量仍保留 | semantic_scenarios |
| “少换乘” | 排序偏好，不等同于“最多一次换乘” | semantic_scenarios |
| 演唱会→用餐→跨城 | 保留活动顺序、开场、散场与用餐时长，比较餐厅与后续交通 | itinerary、intelligent |
| 夜间地铁后打车 | 程序搜索可达下车站并重新查询打车接驳 | night_transfer |
| 赶不上活动、超预算、不允许过夜、不接受骑行 | 淘汰不合格候选；不通过修改用户条件制造成功 | itinerary、intelligent、semantic_scenarios |
| 接口失败、时限和Token限制 | 有限重试、缓存或降级；保留已核验部分与错误状态 | tools_data、api_llm、e2e |

测试文件在 `tests/`。这些是行为回归，并非任意自然语言的理解准确率评测。

## 到达优先的搜索

仅提供到达期限时，先查询较早的可用出发时间，以路线耗时估算 `到达期限 - 耗时 - 15分钟`，再请求供应商重新规划。每个种子最多修正两次，最多三个种子，共享原有工具次数和30秒上限。不能直接平移列车时刻。

第二次修正用于消除“午夜查询包含等待首班数小时”造成的过早出发估计；返回结果仍再次过滤到达期限等硬条件。15分钟是估算时用于留余量的参数，不保证复查后的候选仍恰好提前15分钟到达。搜索不证明最晚可行出发或全局最优。

## 当前边界

- 更复杂的口语改写、否定、条件分支仍可能误解；当前没有无限场景覆盖保证。涉及新站点增删、替代活动时，要检查返回草稿是否符合要求。
- 到达优先的自动倒推目前用于自然语言单程。多站活动主要按固定开场时间和行程顺序向前搜索，尚未实现任意多站网络的完整反向搜索。
- 无障碍电梯、宠物携带、儿童同行、大件行李、卧铺席别、共享单车库存等尚未构成可核验的完整约束体系。
- 地图车次与价格是参考证据；可售日期、席位、机票与实时票价仍需售票方接口，店铺营业与排队也需确认。
- 没查到满足条件的候选仅说明本轮搜索没有找到，不能断言现实无解。
