## 1. 项目概述

### 1.1 项目定位

一个基于大语言模型（LLM）与 LangGraph 编排框架的**多约束混合交通出行智能体**。用户通过自然语言描述复杂出行需求（如"明天晚上从北京海淀到天津滨海新区，预算 100 以内，能接受骑共享单车，不要打车"），智能体自动整合天气、实时车次、多种交通方式（高铁/普速/飞机/大巴/县域班车/轮渡/地铁/公交/网约车/共享单车/步行），在满足硬约束的前提下输出**成本最优、时间合理、可执行**的多套出行方案。

### 1.2 解决的核心痛点

| 痛点 | 主流导航软件的局限 | 本项目的解法 |
|---|---|---|
| **夜间场景失效** | 地铁停运后直接推荐全程打车，忽略"坐末班地铁到最近站再短途打车"的更优解 | 分层搜索支持末班车时间校验 + 接驳策略 |
| **多约束满足差** | 仅支持时间最短/费用最少二选一，无法组合"预算+骑行接受度+换乘容忍度" | 硬约束 + 软偏好双层约束模型，冲突自动检测 |
| **交通方式不全** | 不覆盖县域班车、轮渡、小众路线 | 工具层可扩展，支持网页抓取补充小众交通信息 |
| **方案单一** | 只给一条最优路线，不解释取舍 | 输出 2-3 套方案并标注各自的权衡（省钱 vs 省时 vs 少换乘） |
| **政策问答缺失** | 无法回答"高铁能带充电宝吗""机票退改签规则" | RAG 模块内置出行政策知识库 |

### 1.3 核心特性

- **LangGraph 智能体编排**：ReAct 循环（思考→工具调用→观察→反思→输出），节点清晰可追溯
- **分层混合搜索架构**：LLM 高层决策（需求解析、枢纽选择、方案排序）+ 底层图搜索（时间校验、路径枚举、成本计算），既避免纯 LLM 的班次幻觉，又避免全量图搜索的组合爆炸
- **多交通方式融合**：高铁、普速、飞机、大巴、县域班车、轮渡、地铁、公交、网约车、共享单车、步行
- **夜间场景专项优化**：末班车时间感知、停运后接驳策略、多方案成本对比
- **多约束满足引擎**：硬约束（出发/到达时间窗、预算上限）+ 软偏好（换乘容忍度、骑行接受度、舒适度偏好），冲突时自动检测并给出折中方案
- **RAG 出行政策问答**：Chroma 向量库 + LangChain 检索，覆盖票务规则、退改签政策、安检须知
- **用户偏好记忆**：SQLite 持久化存储，记住骑行接受度、换乘容忍度、预算偏好，下次无需重复输入
- **风险标注体系**：非官方实时数据标注、夜间共享单车覆盖不确定标注、天气影响标注
- **熔断与异常降级**：最大迭代次数、Token 上限、超时控制；工具调用失败自动重试，重试失败给出兜底方案

### 1.4 技术栈总览

| 层级 | 技术选型 | 用途 |
|---|---|---|
| **Agent 编排** | LangGraph + LangChain | 状态机定义、节点编排、工具调用循环 |
| **大模型** | OpenAI GPT-4o / 豆包 Pro / 通义千问（可切换） | 需求解析、规划决策、自然语言生成 |
| **搜索计算** | 自定义分层图搜索（Python） | 主干搜索 + 本地接驳搜索 |
| **RAG** | Chroma + LangChain Embeddings | 出行政策知识库检索 |
| **数据存储** | SQLite | 用户偏好、会话历史、缓存 |
| **API 层** | FastAPI | RESTful 接口 |
| **前端** | Gradio | 对话式交互界面 |
| **工具集成** | Requests / 第三方 API / 网页抓取 | 天气、车次、地理编码 |
| **部署** | Docker + docker-compose | 容器化部署 |
| **测试** | pytest | 单元测试、集成测试 |

### 2.2 分层架构详解

#### 2.2.1 交互层

- **Gradio UI**：面向终端用户的对话式界面，支持自然语言输入、方案卡片展示、方案对比、政策问答
- **FastAPI API**：面向开发者/第三方集成的 RESTful 接口，支持会话管理、规划请求、结果查询
- **CLI 调试**：面向开发者的命令行调试入口，支持单步执行、状态查看、工具模拟

#### 2.2.2 Agent 编排层（LangGraph 核心）

这是整个系统的"大脑"，负责将用户的自然语言需求转化为可执行的多步规划。

**核心设计原则**：
- LLM 只做**高层决策**（需求理解、枢纽选择、方案排序、自然语言生成），不碰原始海量数据
- 底层程序做**精确计算**（时间校验、路径枚举、成本计算、约束过滤）
- 二者通过工具调用接口解耦，LLM 发起搜索请求，搜索层返回结构化结果

**State（全局状态）**：
LangGraph 的 State 是一个 TypedDict / Pydantic Model，在所有节点间共享和传递：

```
State 字段说明：
├── user_id              # 用户标识，用于偏好记忆
├── session_id           # 会话标识
├── user_query           # 用户原始输入
├── parsed_constraints   # 解析后的约束（结构化）
│   ├── origin           # 出发地
│   ├── destination      # 目的地
│   ├── depart_time      # 出发时间（硬约束）
│   ├── arrive_by        # 最晚到达时间（硬约束）
│   ├── budget_max       # 预算上限（硬约束）
│   ├── transfer_tolerance   # 换乘容忍度（软偏好: 0-3）
│   ├── cycling_acceptance   # 骑行接受度（软偏好: 0-2）
│   ├── comfort_priority     # 舒适度偏好（软偏好）
│   └── excluded_modes       # 排除的交通方式
├── intermediate_results # 中间结果集合
│   ├── trunk_candidates # 主干搜索候选
│   ├── local_candidates # 接驳搜索候选
│   ├── weather_info     # 天气信息
│   └── policy_docs      # RAG 检索文档
├── tool_outputs         # 工具调用原始返回（可追溯）
├── final_plans          # 最终方案列表（2-3套）
├── iteration_count      # 当前迭代次数（熔断用）
├── token_usage          # Token 消耗统计
├── errors               # 异常记录
└── risk_labels          # 风险标注集合
```

**节点设计**：

| 节点 | 职责 | 输入 | 输出 |
|---|---|---|---|
| **需求解析节点** | 将自然语言转为结构化约束，提取出发地/目的地/时间/预算/偏好 | user_query, user_preferences | parsed_constraints |
| **规划决策节点** | 决定搜索策略：选择枢纽城市、决定主干交通方式、决定接驳策略 | parsed_constraints, weather_info | search_plan（结构化搜索指令） |
| **工具调用节点** | 根据 search_plan 调用对应工具（天气/车次/搜索/RAG） | search_plan | tool_outputs |
| **结果整合节点** | 将主干搜索 + 接驳搜索结果拼接为完整方案，计算总成本/总时间 | trunk_candidates, local_candidates | combined_plans |
| **反思优化节点** | 评估方案是否满足约束，若不满足则调整策略重新搜索（最多 N 轮） | combined_plans, parsed_constraints | refined_plan 或 终止信号 |
| **输出生成节点** | 将最终方案转为自然语言，注入风险标注，生成用户可读回复 | final_plans, risk_labels | final_response |

**边与循环设计**：

```
需求解析 ──▶ 规划决策 ──▶ 工具调用 ──▶ 结果整合 ──▶ 反思优化
                ▲                                    │
                │                                    │
                └──────────── 不满足约束 ◀───────────┘
                                                     │
                                                     ▼ 满足约束
                                               输出生成 ──▶ END
```

**熔断机制**：
- `max_iterations = 6`：反思优化循环最多 6 轮，超过则强制输出当前最优方案
- `token_limit = 8000`：单次规划 Token 消耗上限，超过则截断中间结果
- `timeout = 30s`：单次规划总超时，超时则返回兜底方案（推荐主流交通方式）
- 熔断触发时记录 `errors` 字段，并在最终回复中标注"方案可能非最优，因计算资源限制"

**异常降级策略**：
- 工具调用失败 → 自动重试 2 次（指数退避：1s → 2s）
- 重试仍失败 → 标记该工具不可用，使用缓存数据或跳过该维度
- 搜索层无结果 → 降级为"推荐单一主流方式"（如高铁直达），并标注"未找到满足全部约束的方案"
- LLM 调用失败 → 降级为规则引擎（基于硬约束的简单筛选）

#### 2.2.3 工具服务层

所有工具遵循统一接口规范，LLM 通过 function calling 调用：

```
工具统一接口：
├── name: 工具名称（英文蛇形）
├── description: 工具描述（LLM 据此选择）
├── parameters: JSON Schema 定义的入参
├── execute(params) -> ToolResult
└── retry_policy: 重试策略（次数、退避间隔）
```

| 工具 | 功能 | 核心入参 | 核心出参 |
|---|---|---|---|
| `weather_query` | 查询目的地/途经地天气 | location, date | temperature, condition, wind, rain_probability |
| `transit_query` | 查询车次/航班/大巴班次 | origin, destination, date, mode | 班次列表（出发/到达时间、价格、余票） |
| `web_search` | 网页搜索（小众交通信息） | query | 搜索结果摘要 + URL |
| `rag_query` | 出行政策知识库检索 | question | 相关文档片段 + 答案 |
| `geocode` | 地理编码（地址↔经纬度） | address 或 lat,lng | 标准化地址 + 经纬度 |
| `user_preference_get` | 获取用户偏好 | user_id | preference 对象 |
| `user_preference_set` | 更新用户偏好 | user_id, preference | 更新结果 |

#### 2.2.4 搜索计算层

这是项目的**核心技术深度所在**，解决"多模态交通图搜索的组合爆炸"问题。

**为什么不能用单张巨型混合图？**
- 节点：全世界城市、县城、乡镇、车站、码头 → 百万级
- 边：高铁、普速、飞机、大巴、县域班车、轮渡、地铁、公交、网约车、共享单车、步行 → 每条边带时间维度（连续变量）
- 状态空间 = 节点数 × 时间粒度 × 方式组合 → 天文数字，A* 完全不可行
- 主流导航软件（高德/百度）靠分层、分模态搜索 + 几百万行工程代码 + 多年迭代实现，个人项目无法复刻

**正确思路：分模态分层搜索 + LLM 做高级拆解**

```
搜索请求
    │
    ▼
┌─────────────────┐
│  LLM 规划决策    │  决定：走哪个枢纽？主干用什么方式？
│  (高层拆解)      │  城市内从哪到哪接驳？
└────────┬────────┘
         │
    ┌────┴────┐
    ▼         ▼
┌────────┐ ┌────────┐
│主干搜索 │ │接驳搜索 │
│(Trunk) │ │(Local) │
└───┬────┘ └───┬────┘
    │           │
    └─────┬─────┘
          ▼
   ┌─────────────┐
   │  方案拼接器   │  主干段 + 接驳段 = 完整方案
   │  (Combiner)  │  计算总成本、总时间、换乘次数
   └─────────────┘
```

**主干搜索（Trunk Search）**：
- 范围：城市间交通（高铁、普速、飞机、大巴、轮渡）
- 输入：出发城市、目的城市（或枢纽城市）、出发时间窗、交通方式偏好
- 算法：基于时刻表的有向无环图搜索，节点为车站/机场，边为班次
- 输出：按"到达时间 × 成本"排序的 Top-K 主干候选

**本地接驳搜索（Local Search）**：
- 范围：城市内交通（地铁、公交、共享单车、步行、网约车）
- 输入：起点（车站/机场）、终点（目的地）、到达时间（用于末班车校验）
- 算法：城市内多模态图搜索，支持末班车时间约束
- 输出：按"时间 × 成本 × 换乘次数"排序的 Top-K 接驳候选

**方案拼接器（Combiner）**：
- 将主干段与接驳段按时间衔接关系拼接
- 校验：主干到达时间 + 换乘缓冲时间（默认 15 分钟）≤ 接驳出发时间
- 计算：总成本 = 主干费用 + 接驳费用；总时间 = 各段时间之和 + 换乘缓冲
- 过滤：不满足硬约束（预算、到达时间）的方案直接剔除
- 排序：按综合评分（成本 40% + 时间 30% + 换乘 20% + 舒适度 10%）排序

#### 2.2.5 数据存储层

| 存储 | 用途 | 数据内容 |
|---|---|---|
| **SQLite** | 结构化数据持久化 | 用户表、偏好表、会话表、规划结果表、缓存表 |
| **Chroma** | 向量知识库 | 出行政策文档（票务规则、退改签、安检须知） |
| **内存缓存** | 高频查询缓存 | 车次查询结果（TTL 30min）、天气查询（TTL 1h） |
| **配置文件** | 环境与模型配置 | API Key、模型选择、熔断参数、搜索参数 |

### 2.3 核心设计决策

#### 决策一：为什么不用纯 LLM 规划？

- **班次幻觉**：LLM 会编造不存在的车次、错误的时间、不准确的价格
- **时效性差**：LLM 训练数据有截止日期，无法获取实时余票、临时调图
- **多约束推理弱**：LLM 在"预算 100 + 晚上 11 点到 + 能骑行"这类组合约束下容易遗漏条件
- **本项目解法**：LLM 只做决策和拆解，精确数据全部来自工具调用和搜索层

#### 决策二：为什么不用全量图搜索？

- 如 2.2.4 所述，状态空间爆炸，计算不可行
- 个人项目无法获取全量交通数据（尤其是县域班车、轮渡等小众方式）
- **本项目解法**：分层搜索将问题拆解为"城市间主干 + 城市内接驳"两个子问题，每个子问题的图规模可控

#### 决策三：为什么用 LangGraph 而不是普通 Agent 框架？

- LangGraph 提供**显式的状态机**，节点和边清晰可定义，适合需要精确控制循环和熔断的场景
- 普通 ReAct Agent 的循环是隐式的，难以在"反思不满足约束时回到规划决策节点"这类复杂跳转中做精确控制
- LangGraph 的 State 可持久化、可回溯，便于调试和用户偏好记忆
- 支持**人工介入节点**（human-in-the-loop），未来可扩展为"方案不满意时让用户选择调整方向"

## 5. 模块详细设计

### 5.1 Agent 模块（LangGraph 核心）

#### 5.1.1 状态管理

**State 设计原则**：
- 所有节点共享同一个 State 对象，节点只更新自己负责的字段
- 中间结果全部保留在 State 中，便于调试和追溯
- 迭代次数、Token 消耗等元数据实时更新，供熔断器读取

**State 字段详解**：

| 字段 | 类型 | 说明 | 写入节点 | 读取节点 |
|---|---|---|---|---|
| user_id | str | 用户标识 | 入口 | 偏好工具、记忆模块 |
| session_id | str | 会话标识 | 入口 | 会话管理器 |
| user_query | str | 用户原始输入 | 入口 | 需求解析 |
| parsed_constraints | Constraints | 结构化约束 | 需求解析 | 规划决策、结果整合、反思 |
| search_plan | SearchPlan | 搜索策略指令 | 规划决策 | 工具调用 |
| tool_outputs | dict[str, Any] | 工具返回原始值 | 工具调用 | 结果整合、反思 |
| trunk_candidates | list[TrunkLeg] | 主干搜索候选 | 工具调用（间接） | 结果整合 |
| local_candidates | list[LocalLeg] | 接驳搜索候选 | 工具调用（间接） | 结果整合 |
| combined_plans | list[Plan] | 拼接后的方案 | 结果整合 | 反思、输出 |
| final_plans | list[Plan] | 最终方案（Top 2-3） | 反思 | 输出 |
| weather_info | WeatherInfo | 天气信息 | 工具调用 | 规划决策、风险标注 |
| policy_docs | list[Document] | RAG 检索文档 | 工具调用 | 输出 |
| iteration_count | int | 当前迭代次数 | 每轮循环 | 熔断器 |
| token_usage | TokenUsage | Token 消耗 | 每次 LLM 调用 | 熔断器 |
| errors | list[ErrorRecord] | 异常记录 | 异常处理器 | 输出 |
| risk_labels | list[RiskLabel] | 风险标注 | 风险标注器 | 输出 |

#### 5.1.2 节点详细设计

**节点一：需求解析节点（parse_requirements）**

- **职责**：将用户自然语言转为结构化约束对象
- **LLM 调用**：是
- **Prompt 设计要点**：
  - 系统提示：定义约束对象的 JSON Schema，明确每个字段的含义和取值范围
  - Few-shot 示例：3-5 个典型输入→输出对（含模糊表达的处理，如"明天晚上"→具体时间窗）
  - 输出约束：严格 JSON 格式，禁止额外文字
- **处理逻辑**：
  1. 从 State 读取 user_query
  2. 调用 preference_tool 获取用户历史偏好（作为补充上下文）
  3. LLM 解析 user_query + 偏好上下文，输出 Constraints JSON
  4. 校验 JSON 合法性（字段完整性、时间逻辑：出发时间 < 到达时间）
  5. 校验失败 → 让 LLM 重新解析（最多 2 次），仍失败则标记错误并使用默认约束
  6. 将 parsed_constraints 写入 State
- **关键约束解析规则**：
  - "晚上" → 18:00-23:59；"凌晨" → 00:00-05:00
  - "尽量便宜" → budget_max 不设上限，但 comfort_priority = low
  - "不要打车" → excluded_modes = ["taxi", "rideshare"]
  - "能接受骑车" → cycling_acceptance = 2（高接受度）
  - "少换乘" → transfer_tolerance = 1

**节点二：规划决策节点（plan_search）**

- **职责**：决定搜索策略，生成结构化搜索指令
- **LLM 调用**：是
- **Prompt 设计要点**：
  - 系统提示：定义 SearchPlan 的 JSON Schema，包含主干搜索参数和接驳搜索参数
  - 上下文：传入 parsed_constraints + weather_info（如果有）
  - 决策引导：提示 LLM 考虑"是否需要选择枢纽城市""夜间场景是否需要调整策略"
- **处理逻辑**：
  1. 读取 parsed_constraints
  2. 如果出发地/目的地是具体地址，先调用 geocode_tool 标准化
  3. LLM 基于约束生成 SearchPlan：
     - 主干搜索：出发城市、目的城市（或枢纽）、出发时间窗、优先方式
     - 接驳搜索：起点（车站/机场）、终点（目的地）、到达时间（用于末班车校验）
  4. 将 search_plan 写入 State
- **SearchPlan 数据结构**：
  ```
  SearchPlan:
    trunk:
      origin_city: str
      destination_city: str
      depart_time_window: [start, end]
      preferred_modes: list[str]
      max_transfers: int
    local_origin:
      start: str (具体地址/车站)
      end: str (出发车站)
      arrive_by: datetime
    local_destination:
      start: str (到达车站)
      end: str (目的地地址)
      arrive_by: datetime
  ```

**节点三：工具调用节点（execute_tools）**

- **职责**：根据 search_plan 调用所需工具，收集结果
- **LLM 调用**：是（通过 function calling 决定调用哪些工具）
- **处理逻辑**：
  1. 读取 search_plan
  2. LLM 通过 function calling 决定调用工具列表（可能并行调用多个）
  3. 对每个工具调用：
     - 执行工具的 execute 方法
     - 失败时按 retry_policy 重试（最多 2 次，指数退避）
     - 重试仍失败 → 记录错误，使用缓存或标记不可用
  4. 主干搜索和接驳搜索通过 transit_tool + 搜索算法完成（搜索层作为工具的内部实现）
  5. 将所有工具结果写入 tool_outputs、trunk_candidates、local_candidates、weather_info 等字段
- **并行调用优化**：天气查询和车次查询无依赖，可并行执行，减少总耗时

**节点四：结果整合节点（combine_results）**

- **职责**：将主干搜索和接驳搜索结果拼接为完整方案
- **LLM 调用**：否（纯程序逻辑）
- **处理逻辑**：
  1. 读取 trunk_candidates 和 local_candidates
  2. 调用 combiner 执行拼接：
     - 对每个主干候选，找到时间衔接的接驳候选
     - 校验换乘缓冲时间（默认 15 分钟，可配置）
     - 计算总成本、总时间、总换乘次数
  3. 过滤不满足硬约束的方案（预算超支、到达时间超时）
  4. 按综合评分排序，取 Top 5
  5. 将 combined_plans 写入 State
- **综合评分公式**：
  ```
  score = 0.40 * (1 / normalized_cost)
        + 0.30 * (1 / normalized_time)
        + 0.20 * (1 / (transfer_count + 1))
        + 0.10 * comfort_score
  ```
  权重可在 search_config.yaml 中调整

**节点五：反思优化节点（reflect_and_optimize）**

- **职责**：评估方案是否满足约束，决定是否需要重新规划
- **LLM 调用**：是
- **处理逻辑**：
  1. 读取 combined_plans 和 parsed_constraints
  2. LLM 评估：
     - 是否有方案满足所有硬约束？
     - 软偏好的满足程度如何？
     - 是否存在明显的搜索策略问题（如枢纽选择不当、遗漏了某种交通方式）？
  3. 决策分支：
     - **满足约束** → 选择 Top 2-3 方案写入 final_plans，进入输出生成节点
     - **不满足约束但有改进空间** → iteration_count + 1，生成调整后的 search_plan，回到规划决策节点
     - **不满足约束且无改进空间 / 达到熔断阈值** → 取当前最优方案写入 final_plans，标注"未找到完全满足约束的方案"，进入输出生成节点
  4. 熔断检查：iteration_count >= max_iterations 或 token_usage >= token_limit → 强制终止
- **反思的 Prompt 设计**：
  - 提供当前方案列表（结构化摘要）
  - 提供约束清单
  - 要求 LLM 输出：是否满足 + 改进方向（JSON 格式：{satisfied: bool, adjustment: str, new_search_params: {...}}）

**节点六：输出生成节点（generate_response）**

- **职责**：将最终方案转为自然语言回复，注入风险标注
- **LLM 调用**：是
- **处理逻辑**：
  1. 读取 final_plans、risk_labels、errors、policy_docs
  2. 调用 risk_labeler 为每个方案生成风险标注
  3. LLM 基于方案 + 标注 + 异常记录生成自然语言回复：
     - 每套方案用清晰的分段展示（方式、时间、费用、换乘点）
     - 方案间对比（省钱 vs 省时 vs 少换乘）
     - 风险标注以醒目标记附在对应段落
     - 如有异常，简要说明（如"部分车次信息可能非实时"）
     - 如有政策问答，附上 RAG 检索的答案和来源
  4. 将最终回复写入 State，返回给用户
- **输出格式设计**：
  ```
  为你找到 2 套方案：

  【方案一：经济首选】约 ¥85，总耗时 3h20m
  1. 22:15 北京西站 乘 G123 → 23:05 天津站（¥54.5）
  2. 23:20 天津站 乘地铁2号线 → 23:45 滨海新区站（¥4）⚠️ 末班车 23:50
  3. 23:50 滨海新区站 共享单车 → 00:10 目的地（¥1.5）⚠️ 夜间覆盖不确定

  【方案二：时间优先】约 ¥120，总耗时 2h40m
  ...

  💡 对比：方案一比方案二省 ¥35，但多 40 分钟，且含夜间骑行。
  ```

#### 5.1.3 图构建与边设计

```python
# 伪代码：graph.py 的核心结构
graph = StateGraph(State)

# 注册节点
graph.add_node("parse", parse_requirements)
graph.add_node("plan", plan_search)
graph.add_node("tools", execute_tools)
graph.add_node("combine", combine_results)
graph.add_node("reflect", reflect_and_optimize)
graph.add_node("output", generate_response)

# 定义边
graph.set_entry_point("parse")
graph.add_edge("parse", "plan")
graph.add_edge("plan", "tools")
graph.add_edge("tools", "combine")
graph.add_edge("combine", "reflect")

# 条件边：反思节点的输出决定下一步
graph.add_conditional_edges(
    "reflect",
    reflect_decision,  # 函数：返回 "replan" 或 "finalize"
    {
        "replan": "plan",      # 不满足约束，回到规划决策
        "finalize": "output",  # 满足约束，进入输出
    }
)

graph.add_edge("output", END)

# 编译
compiled_graph = graph.compile()
```

#### 5.1.4 熔断机制详解

| 熔断维度 | 阈值 | 检查时机 | 触发动作 |
|---|---|---|---|
| 迭代次数 | max_iterations = 6 | 反思节点每次执行后 | 强制取当前最优方案，进入输出 |
| Token 消耗 | token_limit = 8000 | 每次 LLM 调用后 | 截断中间结果（只保留 Top 3），强制进入输出 |
| 总耗时 | timeout = 30s | 工具调用节点开始时 | 返回兜底方案（推荐高铁直达 + 打车接驳） |
| 连续错误 | max_consecutive_errors = 3 | 工具调用失败时 | 跳过该工具，使用缓存或默认值 |

熔断触发时，在 State.errors 中记录熔断类型和原因，并在最终回复中标注。

#### 5.1.5 异常降级策略

| 异常场景 | 降级动作 | 用户感知 |
|---|---|---|
| 车次查询 API 失败 | 重试 2 次 → 使用缓存（TTL 内）→ 跳过该方式，只返回可用方式 | "部分车次信息可能非实时" |
| 天气 API 失败 | 重试 2 次 → 跳过天气维度，不影响规划 | 无天气相关建议 |
| 地理编码失败 | 重试 2 次 → 使用用户输入的原始地址（不标准化） | 搜索精度可能下降 |
| RAG 检索无结果 | 返回"未找到相关政策，建议咨询官方渠道" | 明确告知 |
| 搜索层无结果 | 降级为单一主流方式推荐（如高铁直达），标注"未找到满足全部约束的方案" | 给出可行但非最优的方案 |
| LLM 调用失败 | 重试 1 次 → 降级为规则引擎（基于硬约束的简单筛选） | 方案可能较粗糙 |

#### 5.2.2 主干搜索算法

**算法选择**：时间窗 Dijkstra（Time-Dependent Dijkstra）

**核心思想**：
- 传统 Dijkstra 的边权是固定的，但交通班次的"边权"取决于到达时间（到早了需要等下一班）
- 时间窗 Dijkstra 在松弛边时，根据当前到达时间查询下一班可用车次，计算实际到达时间和成本

**算法伪代码**：
```
function time_dependent_dijkstra(graph, origin, destination, earliest_depart, latest_arrive):
    # 状态：(node_id, earliest_arrival_time, total_cost)
    priority_queue = [(earliest_depart, 0, origin, [])]
    visited = {}  # node_id -> (best_arrival_time, best_cost)
    
    while priority_queue not empty:
        (arrive_time, cost, current, path) = pop_min(priority_queue)
        
        if current == destination:
            return path  # 找到最优路径
        
        if current in visited and visited[current].cost <= cost:
            continue  # 已有更优解
        
        visited[current] = (arrive_time, cost)
        
        for trip in graph.adjacency[current]:
            # 找到 arrive_time 之后的第一班可用车次
            next_trip = find_next_departure(trip, arrive_time)
            
            if next_trip is None:
                continue  # 无可用班次
            
            if next_trip.arrive_time > latest_arrive:
                continue  # 超过最晚到达时间
            
            new_cost = cost + next_trip.cost
            new_path = path + [next_trip]
            
            push(priority_queue, (next_trip.arrive_time, new_cost, next_trip.destination, new_path))
    
    return None  # 无可达路径
```

**多目标优化**：
- 支持两种优化目标：`earliest_arrival`（最早到达）和 `minimum_cost`（最低成本）
- 通过修改优先队列的排序键实现
- 最终返回 Top-K 候选（K=5），覆盖不同权衡

**枢纽选择**：
- 当出发地和目的地之间无直达交通时，LLM 在规划决策节点选择枢纽城市
- 枢纽选择策略：优先选择交通枢纽（如北京、上海、广州、郑州、武汉等）
- 搜索时拆为两段：origin → hub → destination，分别搜索后拼接

#### 5.2.3 本地接驳搜索算法

**与主干搜索的区别**：
- 城市内交通（地铁/公交）的班次是高频的（每 5-10 分钟），不需要精确到每一班
- 共享单车和步行是"随时可用"的，没有时刻表约束
- 末班车时间是关键约束（夜间场景）

**算法**：多模态图搜索 + 末班车约束

```
function local_search(graph, origin, destination, arrive_by, cycling_acceptance):
    # 构建城市内子图（只含 origin/destination 所在城市的节点）
    city_graph = filter_by_city(graph, origin.city)
    
    # 根据骑行接受度过滤边
    if cycling_acceptance == 0:
        remove_edges(city_graph, mode="shared_bike")
    elif cycling_acceptance == 1:
        # 只保留短距离骑行（< 3km）
        filter_edges(city_graph, mode="shared_bike", max_distance=3000)
    
    # 时间窗搜索，额外校验末班车
    results = time_dependent_dijkstra_with_last_train(
        city_graph, origin, destination, 
        earliest_depart=now, 
        latest_arrive=arrive_by,
        last_train_check=True  # 启用末班车校验
    )
    
    return top_k(results, k=3)
```

**末班车校验逻辑**：
- 对每条地铁/公交边，检查 `trip.depart_time <= trip.operating_hours.end`
- 如果计划换乘时间接近末班车（< 10 分钟缓冲），标注"赶末班车风险"
- 如果某段只能坐末班车且之后无替代，标注"夜间方案，错过需打车"

#### 5.2.4 方案拼接器

**拼接逻辑**：
```
function combine(trunk_candidates, local_origin_candidates, local_destination_candidates, constraints):
    plans = []
    
    for trunk in trunk_candidates:
        # 找到与主干出发时间衔接的"出发地→出发站"接驳
        origin_legs = filter_by_time(
            local_origin_candidates, 
            arrive_by = trunk.depart_time - transfer_buffer  # 默认15分钟
        )
        
        # 找到与主干到达时间衔接的"到达站→目的地"接驳
        dest_legs = filter_by_depart(
            local_destination_candidates,
            depart_after = trunk.arrive_time + transfer_buffer
        )
        
        for origin_leg in origin_legs:
            for dest_leg in dest_legs:
                plan = Plan(
                    legs = [origin_leg] + trunk.legs + [dest_leg],
                    total_cost = origin_leg.cost + trunk.cost + dest_leg.cost,
                    total_time = origin_leg.duration + trunk.duration + dest_leg.duration + 2*transfer_buffer,
                    transfer_count = count_transfers(plan)
                )
                
                # 硬约束过滤
                if plan.total_cost <= constraints.budget_max and plan.arrive_time <= constraints.arrive_by:
                    plans.append(plan)
    
    # 评分排序
    scored = [(compute_score(plan, constraints), plan) for plan in plans]
    scored.sort(reverse=True)
    
    return [plan for _, plan in scored[:5]]
```

**换乘缓冲时间**：
- 同站换乘：默认 10 分钟
- 跨站换乘（如火车站→地铁站）：默认 15 分钟
- 含安检的换乘（如机场→地铁）：默认 30 分钟
- 可在 search_config.yaml 中配置

#### 5.3.1 工具基类设计

BaseTool:
  name: str                    # 工具名称（蛇形）

  retry_max: int = 2           # 最大重试次数

  timeout: float = 10.0        # 单次调用超时

    # 子类实现具体逻辑

            return execute(params)

### 5.4 RAG 模块

#### 5.4.1 知识库构建

**文档来源**：
- 12306 官方票务规则（购票、退票、改签、实名制）
- 航空公司退改签政策（国航、东航、南航等主要航司）
- 安检须知（高铁/机场禁止携带物品、充电宝规定）
- 共享单车使用规则（美团、哈啰、青桔）
- 城市地铁运营时间（北京、上海、广州、深圳等主要城市）

**文档处理流程**：
```
原始文档 (Markdown/PDF)
    │
    ▼
文档加载 (DocumentLoader)
    │  - Markdown: 直接读取
    │  - PDF: PyPDFLoader 提取文本
    ▼
文本清洗 (TextCleaner)
    │  - 去除页眉页脚、目录、重复内容
    │  - 统一格式（标点、空格）
    ▼
文档切分 (TextSplitter)
    │  - 按段落切分，每段 500-1000 token
    │  - 相邻段落重叠 100 token（保证上下文连贯）
    │  - 保留元数据（文档名、章节、页码）
    ▼
向量化 (Embedder)
    │  - 调用 Embedding API（OpenAI text-embedding-3-small / 豆包 Embedding）
    │  - 每段文本生成 1536 维向量
    ▼
存入 Chroma (VectorStore)
       - 持久化到 data/chroma/
       - 集合名：travel_policies
```

**切分策略的考量**：
- 政策文档通常有清晰的章节结构，按"章节 + 段落"切分比固定长度切分效果更好
- 每条规则（如"充电宝额定能量不超过 100Wh"）应完整保留在一个 chunk 中，不被切断
- 元数据中保留 `rule_type`（票务/安检/退改签）和 `applicable_mode`（高铁/飞机/通用），便于检索时过滤

#### 5.4.2 检索流程

```
用户问题
    │
    ▼
查询改写 (QueryRewriter)
    │  - LLM 将用户问题改写为更适合检索的关键词
    │  - 例："高铁能带充电宝吗" → "高铁 充电宝 携带规定 安检"
    ▼
向量检索 (VectorRetriever)
    │  - 用改写后的查询生成 Embedding
    │  - 在 Chroma 中做余弦相似度搜索
    │  - 返回 Top-5 相关 chunk
    ▼
重排序 (Reranker)
    │  - 按相关性分数 + 元数据权重重新排序
    │  - 与问题交通方式匹配的 chunk 加权
    │  - 取 Top-3
    ▼
上下文构建 (ContextBuilder)
    │  - 将 Top-3 chunk 的文本拼接为上下文
    │  - 附带来源信息（文档名、章节）
    ▼
答案生成 (AnswerGenerator)
    │  - LLM 基于上下文生成答案
    │  - Prompt 要求：只基于上下文回答，不确定时说"未找到明确规定"
    │  - 答案末尾标注来源
    ▼
最终答案 + 来源
```

```

3. 回答要简洁准确，引用具体条款
4. 在答案末尾标注信息来源

检索文档：

用户问题：{question}

```

| R007 | 熔断触发（迭代/Token/超时） | "因计算资源限制，方案可能非最优" | 中 |
| R008 | 工具调用失败使用了缓存 | "部分信息来自缓存，可能非最新" | 低 |

#### 5.6.2 标注流程

```
方案列表 + 工具结果 + 天气信息
    │
    ▼
标注器 (Labeler)
    │  遍历每条规则，检查触发条件
    │  为每个方案/每段行程生成标注
    ▼
标注列表 (list[RiskLabel])
    │
    ▼
注入器 (Injector)
    │  将标注插入最终回复的对应位置
    │  - 方案级标注：附在方案标题后
    │  - 行程段级标注：附在对应行程段末尾
    │  - 全局标注：附在回复末尾
    ▼
带标注的最终回复
```

**RiskLabel 数据结构**：
```
RiskLabel:
  rule_id: str
  message: str
  severity: enum  # low / medium / high
  target_type: enum  # plan / leg / global
  target_index: int  # 对应的方案或行程段索引
```

## 7. 核心算法与策略

### 7.1 多约束满足模型

**约束分类**：

| 类型 | 说明 | 示例 | 处理方式 |
|---|---|---|---|
| 硬约束 | 必须满足，不满足则方案不可行 | 预算上限、最晚到达时间、出发时间窗 | 过滤阶段直接剔除 |
| 软偏好 | 尽量满足，不满足则降低评分 | 少换乘、骑行接受度、舒适度 | 评分阶段加权计算 |

**约束冲突检测**：
- 在需求解析后，检查硬约束之间是否存在逻辑冲突
- 例：预算 50 元 + 北京到上海 → 不可能满足（最低交通费也超过 50）
- 冲突时 LLM 向用户说明冲突，请求调整（如"预算 50 元无法覆盖北京到上海的交通，是否提高预算或选择更近的目的地？"）

### 7.2 方案评分算法

**综合评分公式**：

```
score = w_cost * cost_score
      + w_time * time_score
      + w_transfer * transfer_score
      + w_comfort * comfort_score
      + w_preference * preference_match_score
```

**各维度计算**：

| 维度 | 计算方式 | 归一化 |
|---|---|---|
| cost_score | 1 / (total_cost / min_cost_in_candidates) | 0-1，越便宜越高 |
| time_score | 1 / (total_time / min_time_in_candidates) | 0-1，越快越高 |
| transfer_score | 1 / (transfer_count + 1) | 0-1，换乘越少越高 |
| comfort_score | 基于交通方式的舒适度评分（飞机=1.0, 高铁=0.9, 普速=0.6, 大巴=0.5, 地铁=0.4, 骑行=0.2, 步行=0.1）的加权平均 | 0-1 |
| preference_match_score | 方案满足用户软偏好的比例 | 0-1 |

**默认权重**（可在 search_config.yaml 中调整）：
```
w_cost = 0.35
w_time = 0.25
w_transfer = 0.15
w_comfort = 0.10
w_preference = 0.15
```

### 7.3 夜间场景专项策略

**问题定义**：
- 夜间（22:00-06:00）地铁/公交陆续停运，主流导航软件常推荐全程打车
- 更优解：坐末班地铁/公交到离目的地最近的站，再短途打车/骑行

**策略实现**：

1. **末班车感知搜索**：
   - 本地接驳搜索时，对每条地铁/公交边检查运营时间
   - 如果计划乘坐的是末班车，在方案中标注"末班车"
   - 如果某段无公共交通可用，自动加入"打车"或"骑行"作为替代

2. **最近站策略**：
   - 当目的地附近的地铁站已停运时，搜索"仍在运营的最近地铁站"
   - 从该站到目的地使用打车/骑行接驳
   - 对比"全程打车"和"地铁到最近站+短途打车"的成本，推荐更优者

3. **多方案对比**：
   - 夜间场景强制输出至少 2 套方案：
     - 方案 A：经济优先（尽量用公共交通 + 短途打车）
     - 方案 B：便捷优先（全程打车或最少换乘）
   - 明确标注两套方案的成本差异和时间差异

### 7.4 成本优先策略

**触发条件**：
- 用户明确说"尽量便宜""省钱""预算有限"
- 或 budget_preference = "economy"

**策略实现**：

1. **搜索阶段**：
   - 主干搜索优化目标设为 `minimum_cost`（而非 `earliest_arrival`）
   - 优先搜索普速列车、普通大巴、红眼航班等低成本方式
   - 接驳搜索优先公共交通，其次共享单车，最后打车

2. **换乘放宽**：
   - 经济优先时 transfer_tolerance 自动 +1（最多不超过 3）
   - 允许更多换乘以换取更低成本

3. **时间放宽**：
   - 经济优先时 arrive_by 约束放宽（如果用户未明确指定到达时间）
   - 允许更早出发或更晚到达

4. **小众方式探索**：
   - 调用 web_search_tool 查询县域班车、轮渡等小众低成本方式
   - 如果找到更便宜的小众路线，纳入候选

## 12. 风险与挑战

### 12.1 技术风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 第三方 API 不稳定（车次/天气） | 规划结果不准确或失败 | 缓存 + 降级 + 多数据源备份 |
| LLM 输出格式不稳定 | 解析失败、流程中断 | 输出格式校验 + 重试 + Pydantic 解析 |
| 搜索结果组合爆炸 | 规划超时 | 分层搜索 + Top-K 截断 + 熔断 |
| 本地交通数据覆盖不足 | 接驳搜索结果差 | 示例数据 + 网页搜索补充 + 标注数据局限 |

### 12.2 数据风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 车次/票价数据非实时 | 用户按方案出行时遇到变动 | 风险标注"非实时数据，建议确认" + 余票查询 |
| 小众交通信息不准确 | 方案不可执行 | 标注"小众方式，建议提前确认" + 提供替代方案 |
| 政策文档过时 | RAG 回答错误 | 定期更新知识库 + 标注文档版本 + 建议咨询官方 |

### 12.3 成本风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| LLM Token 消耗高 | 运行成本高 | 熔断 Token 上限 + 缓存 + 减少不必要的 LLM 调用 |
| 第三方 API 调用费用 | 运行成本高 | 缓存高频查询 + 免费 API 优先 + 调用量监控 |

### 13.2 面试高频问题与回答要点

**Q1：为什么用 LangGraph 而不是普通的 Agent 框架？**
- LangGraph 提供显式状态机，节点和边可精确定义，适合需要控制循环和熔断的场景
- 普通 ReAct Agent 的循环是隐式的，难以实现"反思不满足时回到规划决策节点"的复杂跳转
- State 可持久化、可回溯，便于调试和用户偏好记忆

**Q2：分层搜索架构具体怎么解决组合爆炸？**
- 将"全世界所有交通方式一张图"拆解为"城市间主干图 + 城市内接驳图"两个子问题
- 每个子图的节点和边规模可控（主干：城市级；接驳：城市内）
- LLM 做高层拆解（选择枢纽、决定搜索参数），程序做精确搜索
- 二者通过结构化接口解耦，避免 LLM 直接处理海量数据

**Q3：如何保证方案的时间和费用是准确的？**
- LLM 不生成具体的班次时间和费用，全部来自工具调用（车次 API）和搜索层计算
- 工具结果有数据来源标注，非官方数据标注"仅供参考"
- 方案拼接时做时间衔接校验（换乘缓冲），避免时间冲突
- 余票未知时标注"建议提前购票"

**Q4：熔断机制具体怎么实现的？**
- 三维熔断：迭代次数（6轮）、Token 消耗（8000）、总超时（30s）
- 迭代次数在反思节点每次执行后检查
- Token 在每次 LLM 调用后累计检查
- 超时在工具调用节点入口检查
- 熔断触发时取当前最优方案，标注"因计算资源限制，方案可能非最优"

**Q5：和高德/百度导航比，你的项目有什么优势？**
- 多约束满足：主流软件只支持"时间最短/费用最少"二选一，本项目支持预算+骑行+换乘容忍度等组合约束
- 夜间场景优化：主流软件在地铁停运后推荐全程打车，本项目支持"坐末班到最近站+短途接驳"
- 交通方式更全：支持县域班车、轮渡等小众方式
- 可解释性：输出多套方案并标注各自的权衡，而非只给一条路线
- 政策问答：内置 RAG 知识库，回答票务/安检规则问题
- 诚实定位：个人项目不追求替代专业导航，而是解决"主流软件满足不了的个性化复杂需求"

**Q6：如果让你继续优化，你会做什么？**
